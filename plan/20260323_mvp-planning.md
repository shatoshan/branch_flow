# 20260323 MVP Detailed Planning

## Intent
MVP の像と全体計画を、実装順を迷わない粒度まで落とす。
ここでは、BranchFlow を「少数の条件付きオプション買い候補だけを残す手動運用端末」として定義し、最初の実装境界を固定する。

## Fixed Decisions
2026-03-23 時点の固定事項は以下。
- 初期対象市場は `日経平均` とする
- 初期インターフェースは `ローカル Web UI` とする
- 初期データ入力は `manual-first` とし、まずは手入力で成立させる
- ただし後で楽にするため、入力形は `import-friendly` な構造を保つ
- 価格判定は `最低限ガード` のみで始める
- データモデルは上下両方向に対応し、最初のサンプルは `downside 先行` とする

## Why Downside First
- `reject-first` の思想に合い、見送り条件と kill switch を厳しく設計しやすい
- 恐怖局面では「シナリオは分かるが価格が悪い」を明確に落とせるため、価格ガードの価値が見えやすい
- ただし MVP の器自体は両方向対応とし、後続で upside シナリオを無理なく追加できるようにする

## Working MVP Image
### MVP が毎日返すべきこと
- 何を `Watch` し続けるか
- 何が `Eligible` に昇格したか
- 何を `Rejected` として見送ったか
- 何が `Invalidated` され、仮説が壊れたか

### MVP の利用前提
- 単一オペレーター向け
- 日次レビューが主運用で、日中はトリガー確認のみ
- 出力は常時多件数ではなく、0 件を含む少数候補
- 候補昇格はルールベースで行い、説明文は後付けでよい
- LLM なしでも成立することを優先する

## Planning Assumptions
- 対象市場はまず `日経平均` に絞る
- 初期 UI は `ローカル Web UI` とし、状態一覧とカード閲覧を優先する
- 初期は `manual-first` とし、観測値や価格情報は手入力でよい
- ただし将来の半手動化のため、データ構造は JSON/CSV へ寄せやすい形にする
- `portfolio policy` は別レイヤーに分離し、MVP では参考制約のみ持つ
- 自動売買、発注連携、バックテスト基盤は MVP 範囲外とする
- 価格判定は「最低限の見送り条件」を先に固定し、精緻なバリュエーションは後続に回す

## Scope Freeze For MVP
### 入れるもの
- 日経平均向け監視シナリオの登録と更新
- `Watch / Eligible / Rejected / Invalidated` の状態管理
- 候補カード 10 項目以内の固定
- 価格面の最低判定条件
- ホーム画面と詳細画面の最小ワイヤー
- 理由付きの見送り、失効、昇格履歴

### 入れないもの
- 方向予測スコアのランキング
- 自動発注
- 高頻度トレード支援
- 複数市場をまたぐ同時最適化
- 本格的な IV モデルやヒストリカル検証エンジン

## Recommended MVP Boundary
### オペレーション像
1. オペレーターが日経平均シナリオを `Watch` として登録する
2. 日次更新で観測条件、価格条件、期限条件を見直す
3. 条件が揃ったものだけ `Eligible` に昇格させる
4. 条件未達または価格不適合は `Rejected` に送る
5. 仮説破綻や期限切れは `Invalidated` に送る

### 最初の出力物
- ホーム画面: 4 状態のカード一覧
- 詳細画面: 観測トリガー、想定フロー連鎖、価格メモ、失効条件
- データ雛形: シナリオ 1 件を表現できる構造化フォーマット

- ステータス

## Minimum Price Gate Draft
MVP の価格判定は、まず「買ってはいけない条件」を落とすための下限ガードに留める。

### 初期ルール案
- 期限が短すぎてイベント前後の時間価値毀損に弱すぎないこと
- スプレッドが広すぎず、約定しにくい銘柄を避けること
- プレミアム額が 1 回の損失予算を超えないこと
- 既知イベント直前で IV が過熱している場合は見送れること
- 同一テーマで直近に連続エントリーしている場合は頻度制限をかけられること

### 後続に回すもの
- IV percentile
- RV/IV 比較
- スキュー詳細
- イベント別の期待変動レンジ比較

## Delivery Sequence
### Phase 2A: Definition Freeze
目的: MVP の境界と 1 ページ仕様を確定する

成果物:
- 詳細 planning
- MVP one-pager
- 候補カード項目の固定
- 状態遷移定義
- 最低価格判定条件

完了条件:
- 対象市場が固定されている
- カード項目が 10 個以内
- 4 状態の意味が一意
- 最初に作る画面とデータ構造が決まっている

### Phase 2B: Manual Ops Spec
目的: コード前に運用フローと入力雛形を固定する

成果物:
- 1 日の運用ループ
- 手入力の手順
- 手入力を楽にする候補手段の整理
- サンプルシナリオ 3 件程度
- 観測値の記録テンプレート

完了条件:
- 同じシナリオを別日に再評価できる
- `Rejected` と `Invalidated` の理由が記録できる
- 後で半手動化できる入力構造になっている

### Phase 3: Product Skeleton
目的: 最初の UI 骨格と状態遷移を実装できる状態にする

成果物:
- ホーム画面ワイヤー
- 詳細画面ワイヤー
- 状態遷移図
- 最小データモデル

完了条件:
- ホームから詳細へ遷移できる
- 4 状態の一覧と理由表示ができる

### Phase 4: Prototype Build
目的: 手動運用を支える最小プロトタイプを作る

成果物:
- シナリオ CRUD の最小形
- 状態変更ロジック
- 価格ガード入力
- 履歴またはメモ欄

完了条件:
- 1 日分の更新がプロトタイプ上で完結する
- 0 件出力でも正常終了できる

### Phase 5: Post-MVP Extensions
後続で追加するもの:
- 外部データ取得の自動化
- 市場追加
- `portfolio policy` レイヤー
- LLM による要約と説明
- 観測候補抽出の補助

## Resolved Decisions
### D1. 初期対象市場
- 決定: `日経平均` 先行
- 理由: データ語彙、価格ルール、サンプル設計を先に狭く固定するため

### D2. 初期インターフェース
- 決定: `ローカル Web UI`
- 理由: 4 状態一覧、カード比較、詳細画面の視認性を優先するため

### D3. 初期データ入力方式
- 決定: `手動入力` 先行
- 理由: MVP 到達を速めつつ、後で楽にする余地を残すため

### D4. 価格判定の厳しさ
- 決定: `最低限ガードのみ`
- 理由: まずは高すぎる候補を落とす最低線を固定する方が重要なため

### D5. 最初の戦う方向
- 決定: データモデルは `両方向対応`、サンプルは `downside 先行`
- 理由: reject-first と kill switch を強く設計しやすいため

## Risks To Control
- 予測アプリ化して状態説明よりも相場観を前面に出してしまう
- 日経平均の運用仕様を固める前に対象市場を増やしてしまう
- 価格判定を後回しにして「良い話だが高すぎる候補」を通してしまう
- 自動化を急ぎすぎて MVP の手動運用検証が抜ける
