# BranchFlow Foundation

## 目的
BranchFlow は、相場を予測するためのツールではない。
不確実性の中で、個人投資家が何を見送り、何を監視し、どの条件が揃ったときだけ小さく賭けるかを整えるためのシナリオ端末である。

この文書は、ここまでの壁打ちで固まった前提、批判点、設計思想、プロダクト定義、将来の実装方針をまとめた基礎設計メモである。

## 背景
- 予測不能性を前提にしている。強い方向予想を出すことは目的ではない。
- 用途は、日経平均または S&P のオプション買いにおいて、条件付きで期待値の歪みがありそうな局面を少数だけ抽出すること。
- ただし、オプション買いは時間価値、IV 水準、イベント前後のボラ収縮に負けやすく、シナリオが当たってもトレードが勝つとは限らない。
- そのため、価値の中心は「勝てる候補を大量に見つけること」ではなく、「低品質な候補を大量に除外すること」に置く。

## このプロダクトが解く問題
- 情報が多すぎて、個人投資家が何を見ればよいか分かりにくい。
- 相場観が強くなりすぎると、見送りや失効が難しくなる。
- マクロ、中央銀行、フロー、オプション市場の情報が分断されており、条件付きの賭けとして整理しにくい。
- 予測不能性を認めても、どの条件が揃うまで待つべきかを運用手順に落としにくい。

## プロダクト定義
BranchFlow は、以下を行う運用OSである。
- 監視すべき条件を定義する
- 候補を除外する
- 条件が揃ったときだけ候補へ昇格させる
- 仮説の失効条件を明示する
- 少数の非対称な賭けだけを残す

BranchFlow は、以下ではない。
- 価格予測アプリ
- 常時シグナルを出し続ける売買ツール
- LLM による相場解説生成機
- バーベル戦略を単体で完結させるポートフォリオ管理システム

## 基本思想
### 予測不能性
- 将来の方向を当てることはできないという前提に立つ。
- 予想ではなく、条件付き仮説とその更新だけを扱う。

### 除外優先
- 候補抽出よりも先に、買ってはいけない場面を落とす。
- `No trade` は正常な出力である。

### 条件待ち
- トリガー未観測の仮説は保留し、見切り発車を避ける。
- 観測条件、行動条件、失効条件を常にセットで扱う。

### 価格も仮説と同格
- シナリオが良くても、オプション価格が悪ければ見送る。
- マクロやフローだけで昇格を決めない。

## 5 Principles
1. Predict less, specify more
方向予想を増やすのではなく、観測条件と行動条件を明確にする。

2. Reject first
候補を探す前に、買ってはいけない場面を先に落とす。

3. No trade is a valid output
見送りを失敗ではなく正常出力として扱う。

4. Every scenario needs a kill switch
すべての仮説に失効条件と見直し時点を持たせる。

5. Price matters as much as thesis
シナリオ強度だけでなく、オプション価格の良し悪しを同格で扱う。

## Non-Goals
- 予測精度を競わない
- 常時ポジションを持つことを目指さない
- 面白い相場解説を目的化しない
- シグナル量の多さを価値にしない
- ブラックボックスな判定に依存しない

## 想定ユーザー
- 予測不能性を前提にしつつ、市場に参加したい個人投資家
- 相場観よりも運用規律を重視したい人
- オプション買いを、少数の非対称な賭けとして扱いたい人
- 情報過多やポジション依存を避けたい人

## ユースケース
主要ユースケースは以下。
- 日経平均または S&P のオプション買い候補の監視
- 既知イベントそのものではなく、観測されると片方向にフローが自己増幅しやすい分岐条件の監視
- 候補の昇格前に、マクロ・フロー面の仮説とオプション価格面の妥当性を両方確認
- 候補が失効した場合の即時降格

## 戦略に対する批判的評価
### 良い点
- 条件、失効、観測ソースを構造化することで、裁量判断の質を上げられる。
- 中央銀行解釈変更、金利再価格、為替連鎖、システマティック勢の追随など、自己増幅しやすい局面に絞れば有用性が高い。
- 高頻度で当てることではなく、壊れにくい意思決定を支えられる。

### 弱い点
- プレーヤー観測の多くは遅く、粗く、代理変数である。
- 説明力の高いシナリオが、そのまま価格に対する優位性を意味しない。
- オプション買いは方向だけでなく、期限、IV、水準、イベント前後の収縮まで考慮が必要で難しい。
- 候補を絞らなければ、単なるプレミアム払いの繰り返しになりやすい。

### 設計への含意
- 主価値は「当てること」ではなく「除外すること」に置く。
- シナリオ強度とオプション価格判定の二段階構造が必要。
- 取引頻度制御と損失予算が必要。

## タレブ的バーベル戦略との関係
BranchFlow 単体は、タレブのバーベル戦略そのものではない。
担えるのは、バーベルの危険側ウィング、つまり少額の凸性エクスポージャーの選別層である。

バーベルとして成立させるには、別レイヤーで以下が必要になる。
- 安全側資産配分
- プレミアム損失予算
- 最大取引頻度
- 月次最大損失許容
- リバランス規律

将来的には、BranchFlow の上位に `portfolio policy` レイヤーを置く構成が自然である。

## LLM 統合方針
### 基本方針
- LLM は組み込むべきだが、中核判定エンジンには置かない。
- LLM の役割は `compression and explanation layer` とする。
- 候補昇格、価格判定、資本配分、失効適用は構造化データと明示ルールで扱う。

### LLM に向く役割
- 中央銀行文書、議事要旨、ニュース、レポートの要点抽出
- 既存シナリオとの差分要約
- 候補カードの説明文生成
- 観測トリガー候補の自然言語整理
- ユーザーの自然言語による探索支援

### LLM に向かない役割
- 最終的な候補昇格判定の単独実行
- IV の割高割安判定
- ポジションサイズ決定
- バックテスト評価の自動採点
- 出所不明の相場解釈の中核ロジック化

### 実装順
1. LLM なしで MVP を成立させる
2. 文書要約とシナリオ説明に LLM を追加する
3. 探索 UI や質問応答に LLM を追加する
4. 厳格なガードレール付きで観測候補抽出を補助させる

## MVP 範囲
### 対象市場
- 日経平均
- S&P
- 周辺の金利、為替、政策イベントを補助入力として扱う

### MVP の主目的
- 候補を増やすことではなく、少数の候補を残すための除外フィルターを作る
- `Watch / Eligible / Rejected / Invalidated` の状態管理を確立する
- 候補カードの最小入出力を定義する

### 状態定義
- `Watch`: 仮説はあるが、まだ条件が揃っていない
- `Eligible`: 条件が揃い、価格面も最低限通過している
- `Rejected`: 価格、頻度、品質などの理由で見送り
- `Invalidated`: 監視中または候補中だった仮説が失効

## 情報設計
### 主画面
- 本日の候補カード
- 監視中シナリオ
- 失効したシナリオ

### 補助画面
- シナリオ詳細
- レーダー画面
- ラボ画面

### シナリオ詳細で持つもの
- プレーヤー連鎖
- 観測トリガー
- オプション価格対比
- 過去類似局面
- 失効条件

## 候補カードの考え方
出力の主役は、マインドマップではなくオプション買い候補カード。

カードには最低限以下を持たせる想定。
- 対象指数
- 方向
- 期限
- 観測トリガー
- 想定フロー連鎖
- 価格面の要約
- 失効条件
- ステータス

詳細な項目数は MVP 定義タスクで 10 個以内に絞る。

## データ観測の考え方
- 直接観測できないプレーヤーが多いため、代理指標で近似する
- 更新頻度の異なるデータを同列に扱わない
- 週次や月次のフロー情報は構造判断に使い、最終昇格は価格面で再確認する

利用候補となるデータ群の例。
- JPX 投資部門別売買状況
- CFTC COT
- FRED 系列
- 中央銀行の声明、議事要旨、会合日程
- Treasury TIC
- SEC/EDGAR 13F

## 個人投資家にとっての意義
- 強い相場観ではなく、不確実性を扱う手順を提供する
- 待機、見送り、条件付きエントリー、失効管理を制度化できる
- 情報過多や相場観の暴走を抑えられる
- 高頻度で当てることではなく、壊れにくい意思決定を続けられる

## 運用ループ
- 朝: 監視条件の更新と候補除外
- 日中: トリガー観測時のみ候補化
- 引け後: 継続、保留、失効を再分類
- 週次: 除外精度と失効条件を見直す

## 直近の実務タスク
1. MVP の 1 ページ定義を確定する
2. 候補カード項目を 10 個以内に絞る
3. 状態遷移の定義を固定する
4. 価格面の最低判定条件を決める
5. 将来の `portfolio policy` レイヤーとの境界を決める

- 過去類似局面の定義をどの粒度で作るか
- LLM による観測候補抽出をいつ導入するか
